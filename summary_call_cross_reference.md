# The CallProcessor: Connecting the Dots in the Knowledge Graph

This document provides a detailed analysis of the `CallProcessor`, explaining its workflow and how it uses `tree-sitter` and type inference to resolve function and method calls.

### 1. Introduction

The `CallProcessor` is the final and perhaps most crucial component in the graph building pipeline. It is responsible for the third pass of the analysis, where it "connects the dots" by identifying and resolving all the function and method calls within the codebase. Its primary purpose is to create the `CALLS` relationships in the knowledge graph, which are essential for understanding the flow of execution and the dependencies between different parts of the code.

### 2. Core Responsibilities

The `CallProcessor` has a few, very important responsibilities:

*   **Call Site Identification**: It traverses the Abstract Syntax Tree (AST) of each file to find all the locations where a function or method is called.
*   **Call Resolution**: For each call site, it performs a sophisticated analysis to determine the exact function or method that is being invoked.
*   **Graph Ingestion**: Once a call is resolved, it creates a `CALLS` relationship in the graph, linking the calling function/method to the callee.

### 3. The `process_calls_in_file` Workflow

The `process_calls_in_file` method is the entry point for analyzing a single file. It operates on the cached AST that was generated by the `DefinitionProcessor` in the previous pass. Here is its workflow:

1.  **AST Retrieval**: It receives the pre-parsed AST for a file, avoiding the need to read and parse the file again.
2.  **Contextual Processing**: It processes calls in different contexts within the file:
    *   Inside top-level functions (`_process_calls_in_functions`).
    *   Inside class methods (`_process_calls_in_classes`).
    *   At the module level (for things like Immediately Invoked Function Expressions or IIFEs) (`_process_module_level_calls`).
3.  **Call Ingestion**: For each context (e.g., for each function), it calls `_ingest_function_calls`.

### 4. The Call Resolution Process (`_ingest_function_calls` and `_resolve_function_call`)

This is the core logic of the `CallProcessor`. For each function or method (the "caller"), it performs the following steps:

1.  **Local Type Inference**: It first calls the `TypeInferenceEngine` to build a map of all the local variables within the caller's scope and their inferred types. This is a critical step for accurately resolving method calls (e.g., if it knows `my_var` is an instance of the `User` class, it can resolve `my_var.get_profile()`).
2.  **Executing Tree-sitter Queries**: It executes the `calls` query (as defined in `language_config.py`) against the caller's AST node. This query is designed to find all the nodes that represent a function or method call.
3.  **Iterating Through Call Sites**: For each call site found, it performs the following resolution strategy in `_resolve_function_call`:
    *   **Phase 1: High-Confidence Resolution (Imports)**: It first tries to resolve the call with the highest degree of accuracy by checking the file's import map.
        *   **Direct Imports**: If the `call_name` (e.g., `do_something`) was directly imported, it can be resolved immediately to its fully qualified name.
        *   **Qualified Calls**: For calls like `my_module.do_something()`, it checks if `my_module` was imported.
        *   **Method Calls (`my_object.do_something()`)**: This is where the local type inference pays off. It looks up the type of `my_object` in the `local_var_types` map. If the type is known, it can construct the fully qualified name of the method (e.g., `my_project.models.User.do_something`). If the method is not found directly on the class, it will then walk the inheritance hierarchy (`class_inheritance` map) to find the method on a parent class.
    *   **Phase 2: Heuristic-Based Resolution**: If the high-confidence methods fail, it falls back to a heuristic-based approach.
        *   **Same-Module Check**: It checks if there is a function with the same name defined in the current module.
        *   **Global Trie Search**: As a last resort, it searches the entire `function_registry` for any function or method that ends with the `call_name`. This can be imprecise, especially for common names like `get` or `init`, but it's a useful fallback.
4.  **Handling Special Cases**: The processor has special logic for handling:
    *   **`super()` calls**: It uses the class context and inheritance information to resolve calls to parent class methods.
    *   **Method Chaining**: It can resolve chained calls like `obj.method1().method2()` by inferring the return type of `method1()`.
    *   **Built-in Functions**: It has a list of known built-in functions for languages like JavaScript to avoid trying to find them in the user's code.

### 5. Creating the `CALLS` Relationship

Once `_resolve_function_call` returns a resolved qualified name for the callee, the `CallProcessor` uses the `MemgraphIngestor` to create a `CALLS` relationship in the graph. This relationship is directed from the caller's node to the callee's node.

### 6. Conclusion

The `CallProcessor` is the component that brings the knowledge graph to life. While the `DefinitionProcessor` builds the inventory of all the code elements, the `CallProcessor` builds the connections between them. Its sophisticated, multi-phase resolution strategy, heavily reliant on the `TypeInferenceEngine` and the data structures built in the previous passes, is what enables the system to create a rich and accurate representation of the codebase's runtime behavior. This detailed call graph is what makes it possible to ask complex questions about code flow and dependencies.
